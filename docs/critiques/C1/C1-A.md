### C1-A.2 — The history the design assumes does not exist and nothing builds it
**Location:** Breakdown F2 scope; Standards §Stack "Deployment: Vercel, daily cron snapshots price history to Supabase" and §Conventions "Snapshots keyed by `(scryfall_id, finish)`".
**Hole:** Three facts compound. (2) The cron GET `/api/prices/snapshot` iterates `prisma.trackedCard.findMany()`; the only writer of `tracked_cards` is the POST path with `cardIds`, called by V1's Refresh button, and V1 was removed in cb4737d (2026-04-25) — `src/store/watchlist.ts` is imported by nothing. New cards never acquire history. (3) Spec §3 returns `insufficient_data` when `history.length < minSnapshotsForVerdict (=1)`, so F2's happy path yields `insufficient_data` for essentially every card a user types. The action file's Phase 1 DoD ("computed from MTGJson historical prices… real verdicts, not `insufficient_data`") and its B2–B7 pipeline + destructive schema migration are absent from the Breakdown, the 8 Task DB tasks, and the 9-story cut.
**Evidence:** `schema.prisma` lines 18–33; `snapshot/route.ts` `snapshotAllTrackedCards()`; `git show --stat cb4737d` ("V1 removed… Kept for V2 wiring: src/store/watchlist.ts"); grep shows no importer of `store/watchlist`; action file §B3/§B4/§Definition of done; investigation §9 schema + "Migration script: 1. Drop existing price_snapshots".
**Proposed fix (RULING):**
- **A — Add F0 "Price-history pipeline (MTGJson)" to Phase 1** (B2–B7 of the action file: narrow `price_snapshots` keyed `(card_id, date, provider, finish, list_type)`, bulk ingest script, 17:00 UTC sync replacing the V1 cron, `getPriceHistory`). Destructive migration → falls under C1-A.5's dump rule. Honest cost: +1 feature, +2–3 stories, the Pro-tier question before Phase 2.
- **B — Re-scope Phase 1 to current-price-only Tier 1**: delta needs only Scryfall `prices.usd`; set `minSnapshotsForVerdict = 0`, force `confidence = 'low'` and render history tiles as "—" until a pipeline exists; move F3 (needs 30 snapshots) to Phase 2 explicitly.
- **C — Cold-start fallback**: write one snapshot per evaluated card at evaluation time (self-populating history); cheap, but 30-day confidence takes 30 days per card.
- **Recommend A** if the sprint intent of Aug 5 still stands; otherwise B, stated plainly in the Breakdown so the DoD stops promising history-backed verdicts. Whatever is chosen, the Standards' "daily cron snapshots price history" line must describe the real mechanism.

### C1-A.5 — Migration policy: two engines, no baseline, no backup rule
**Location:** Standards §Pending 4; §Conventions (no migration rule exists).
**Hole:** The gate brief's four rules are phrased for the Supabase CLI (`supabase db diff/reset/push/dump`). The repo's schema is owned by Prisma 7 (`prisma.config.ts` sets `migrations.path = "prisma/migrations"`), but that directory has never existed in git history — prod was created with `npx prisma db push` (README §Database Setup). Consequences the page doesn't address: (i) the first `prisma migrate deploy` against the live DB fails with P3005 "database schema is not empty" unless a baseline migration is generated and marked applied; (ii) the "normal deploy path" applies no migrations — Vercel build is `prisma generate && next build`; (iii) Supabase Free has no automated backups or PITR, so the F0/MTGJson drop of `price_snapshots` (and any later destructive DDL) needs the manual-dump rule written down, not implied; (iv) Prisma Migrate and Supabase CLI both writing migration tables on the same DB is a conflict, not a complement.
**Evidence:** `git log --all -- prisma/migrations` → empty; `ls prisma` → `schema.prisma` only; package.json `build`; gate briefs §Mox P1 rules 1–4; investigation §9 "Migration script: 1. Drop existing price_snapshots".
**Proposed fix (RULING):** **A (recommended)** — Prisma Migrate owns the schema; write the four rules tool-agnostically into §Conventions: (1) every prod schema change is a committed `prisma/migrations/<ts>_slug/migration.sql`, never dashboard DDL; (2) one deploy channel — `prisma migrate deploy` run from the laptop (later a GitHub Action), never both, and never inside the Vercel build; (3) manual `pg_dump`/`supabase db dump` immediately before any DROP/rename/type-narrow, link the dump in the PR; (4) destructive DDL carries a rollback note in the migration header, prefer expand/contract. S1.1 adds the baseline migration (`prisma migrate diff --from-empty --to-schema-datamodel` → `migrate resolve --applied`). **B** — Supabase CLI owns the schema and Prisma consumes it via `prisma db pull` (loses Prisma's typed migration flow; only sensible if Josh wants branching later). Decision 4's actual question ("may Bitey author migrations") is answered yes by the protocol's 4a ERD-update step; replace it with the policy text.

### C1-A.11 — F4 "age" is not free

### C1-A.12 — F5 write path collides with the RSC-reads convention
**Location:** Breakdown F5 scope; Standards §Conventions bullet 5.
**Hole:** Standards: "server components for reads, Server Actions / route handlers only where interaction demands" and "recommendations computed in RSC/server context, shipped as rendered HTML". F5: "server-side write on every computed recommendation". If compute happens in the RSC (as the Standards say), the log write happens during a GET render — fired by crawlers, prefetches, back-button, and every refresh — and the F2 design's "one per compute, not per render" has no definition of compute. "No PII" is asserted next to a free-text reason field and an "abuse guard", which needs an IP-derived key to work. The Standards contain no conventions for side effects in render, hashing, retention, or free-text limits.
**Proposed fix:** Standards §Conventions add: "No DB writes during RSC render. Writes happen in the Server Action/route handler that performs the compute, keyed by an idempotent `evaluationId` passed to the page; log row stores `(scryfall_id, finish, asking_cents, market_cents, kind, confidence, params_version, bucket, ip_hash(salted, daily rotation))`; free-text ≤ 140 chars, stripped, retained ≤ 90 days." Breakdown F5: replace "on every computed recommendation" with "once per submitted evaluation".
