## Detail

### C1-D.1 — Tier 2 formula drops the Buy-side asymmetry
**Location:** F3 §Functionality, trend bullet; spec §3 Tier 2 lines 184–185; F1 example C; S3.2 AC-1.
**Hole:** F3 writes `buyThreshold = −band + shift`. F1 (the engine F3 "extends") bakes in `asymmetry 0.6` and recomputes C as buy < −14.33 (= −5/0.6 − 6). S3.2 AC-1 writes "band 10% → buy threshold −16.67%" (= −10/0.6). The text and the two fixtures disagree.
**Evidence:** Spec §10 Resolved 2026-05-01 propagation trail: "§ 2 parameters table + VERDICT_PARAMS const + § 3 Tier 1 algorithm all updated" — Tier 2 (§3 lines 178–185) was not, and still reads `fairBand = fairBandPct * volWiden * confWiden; buyThreshold = -fairBand + trendShift`. F3 copied that. Recompute of C under the literal F3 text: buy −11 / wait −1 (kind still Fair, so AC-1's kind passes but its pinned thresholds fail). Recompute of S3.2 AC-1 under the literal text: buy −10, delta −12 → Buy, AC expects Fair → the implementer hits a red test and must ask.
**Proposed fix:** Replace the bullet with: "`fairBand = fairBandPct × volWiden × confWiden`; `buyThreshold = −(fairBand / buyThresholdAsymmetry) + trendShift`; `waitThreshold = +fairBand + trendShift`. Order: widen → asymmetry on the Buy side → shift both." (Widen-then-divide and divide-then-widen are algebraically identical; state it once so nobody debates it.) Also file a one-line correction against spec §3 Tier 2.

### C1-D.2 — volWiden formula contradicts its own parameter and the canonical fixture
**Location:** F3 §Functionality volatility bullet; F3 param table rows `volatileCV` and `volatilityWideningCap`; S3.1 AC-1; spec §4 example A.
**Hole:** `min(1 + CV/0.15, 2.0)` is continuous from CV 0 and saturates at CV 0.15 — the number the table calls the CV that "begins widening". Under the literal formula example C (CV 0.07) has volWiden 1.467, band 7.33, thresholds −18.22 / +1.33; AC-1 pins −14.33 / −1 and (once S3.2 lands) `bandPct` would read 7.33.
**Evidence:** Recompute above. Spec §4 A states "volWiden = 1.0 (low CV)" for CV 0.07 — the spec's author also believed widening is gated. Checked S3.2 AC-1 and AC-5 against a gated alternative: CV 0.30 → 2.0 (Fair), CV 0.05 → 1.0 (Buy), CV 0 → 1.0 — all still pass. Under the literal formula CV 0.05 gives 1.333 and Buy by only 0.89 points.
**Proposed fix:** `volWiden = clamp(CV / volatileCV, 1.0, volatilityWideningCap)` — 1.0 up to CV 0.15, continuous there, 2.0 at CV 0.30. Update the table meaning to "CV at which widening begins (1.0×); cap reached at 2× this value". Note for Josh: this is a FIX because every stated example and the param semantics imply it, but it changes behaviour for every card with 0 < CV < 0.15 relative to the literal text, so say which you meant.

### C1-D.3 — The trend threshold gates the label but not the shift; the canonical fixture is sub-threshold
**Location:** F3 table `trendThresholdPct`; F3 "Trend shifts both bands (not a separate vote — monotonic and explainable)"; S3.1 AC-1; F1 copy "trend clause (F3) '30-day trend is {rising/falling} {X}%'".
**Hole:** Example C's slope is −0.4%/day; |−0.4| < 0.5 ⇒ `trendDirection = flat`. AC-1 demands the reason contain "falling 12%". Both cannot hold. Conversely a +0.45%/day card is "flat" yet shifted +6.75: buy < −1.58, so a −2% ask is Buy with the reason "2% below market; trend is flat." That is the "unexplainable verdict" the design says it avoids.
**Evidence:** Recompute: +0.45/day → thresholds −1.58 / +11.75. F1 owns `trendDirection` (S1.2 AC-7 asserts it exactly) but the only threshold is in F3's table, which F1 lists as "dark until F3 lands" — so S1.2 cannot even compute the label it is asked to assert.
**Proposed fix (RULING):** A) Dead zone — `trendShift = 0` when |slope30dPct| < trendThresholdPct, label and shift from the same test; re-pin example C at −0.6%/day (−18%/30d, shift −9 → buy < −17.33, wait > −4; −9.2 still Fair; reason "falling 18%"). B) Keep the shift continuous and lower the threshold to ±0.1%/day (±3%/30d) so a shifted band is always labelled. C) Drop the threshold; label by sign with a ±1%/30d epsilon. Recommendation: A — it is the only option under which "trend is flat" and "band unshifted" mean the same thing to a user. Whichever is chosen, move `trendThresholdPct` into the F1 param list since S1.2 needs it.

### C1-D.4 — S3.1 AC-2 is computed against the superseded ±3% band
**Location:** S3.1 AC-2.
**Hole:** "example A history" is flat in F1 (A was recomputed as "30 daily snapshots, flat" in the r1 pass); only the vault spec's A is rising (+8.1%/30d). With +8.1%: shift +4.05, buyThreshold −8.33 + 4.05 = −4.28; a −2% delta is Fair. The spec's "+1.05" Buy-eligibility came from −3 + 4.05 under the old symmetric 3% band.
**Evidence:** Recompute table above. For −2% to be Buy you need shift > 6.33 → monthlyTrend > 12.67% → slope > 0.42%/day (and ≥ 0.5%/day to also be "rising" under the current threshold).
**Proposed fix:** "AC-2: rising fixture (30 daily snapshots, slope +0.6%/day = +18%/30d, CV < 0.15) → shift +9, buyThreshold = +0.67, waitThreshold = +14; a −2.00% delta → **buy**, reason contains 'rising 18%'." Add it to the canonical fixture set as A′ so F1's A can stay flat.

### C1-D.5 — "%/day" slope has no denominator and no interval convention
**Location:** F3 trend bullet; F1 signals `slope30dPct`; S3.1 AC-1; S1.2 AC-7.
**Hole:** OLS of priceCents on day index yields cents/day. Dividing by the first price, the window mean, the last price, or regressing log prices gives different %/day; "× 30" on a 30-snapshot window (29 intervals) is a second ambiguity. Every trend fixture's expected thresholds depend on the choice, and AC-1 pins them to two decimals.
**Evidence:** Linear 30-point series 8150 → 7172 (−12% endpoint to endpoint): slope/first −0.414%/day (monthly −12.41, thresholds −14.54 / −1.21); slope/mean −0.440 (−13.21; −14.94 / −1.60); slope/last −0.470 (−14.11; −15.39 / −2.05). A series defined as `p_i = 8150 × (1 − 0.004 i)` gives exactly −0.4%/day over the first price but only −11.6% endpoint move. Nothing in F1/F3/spec resolves this.
**Proposed fix:** Pin in F1 (signal owner) and reference from F3: "`slope30dPct` = OLS slope of `priceCents` on UTC-day index (real rows only; gaps need no interpolation under OLS) ÷ mean `priceCents` of the window × 100. `monthlyTrend = slope30dPct × 30` regardless of row count. Fixtures are generated from the slope definition, not from endpoints." Then recompute and re-pin C's thresholds from the generated series (they will not be exactly −14.33 / −1 under any denominator unless the series is built to make them so).

### C1-D.6 — Density is redundant with the count rule in a fixed 30-day window
**Location:** F3 liquidity bullet; S3.2 AC-3; F1 "all snapshot counts, confidence tiers, and density calculations use the trailing 30 UTC days".
**Hole:** density = count / 30. density < 50% ⇔ count ≤ 14. F1 already gives low for count < 14. The liquidity rule therefore changes exactly one case (count = 14, 46.7%), or two under S3.2's "≤50%" (15 = 50.0%). It is not a third axis; staleness is the only new information. The design/AC disagree on < vs ≤; 30 vs 31 UTC dates in the denominator decides whether 15 is 50.0% or 48.4%; "latest > 7d old" needs a clock the pure engine does not have (F1's `MarketSnapshot.fetchedAt` is the obvious `asOf`, unstated).
**Evidence:** Table in recompute: n=14 → 46.7%/45.2%; n=15 → 50.0%/48.4%; n=16 → 53.3%/51.6%. S3.2 AC-3 "≥14 total snapshots with ≤50% density" is satisfiable only with n ∈ {14, 15}.
**Proposed fix (RULING):** A) Drop density; keep staleness (`asOf − latest.date > 7d → low`); rename the axis "freshness". B) Redefine density over a recent sub-window that the count rule cannot see — e.g. `recentDensity = rows in last 14 UTC days / 14 < 0.5 → low` — which catches a card with 20 old rows that went quiet. Recommendation: B, plus "≤" vs "<" settled as "<" to match the design, denominator = 30 (UTC dates `asOf−29 … asOf`), `asOf = market.fetchedAt`.

### C1-D.7 — Dark launch is specified for `kind` only; no shadow-output contract exists
**Location:** F3 W2 steps 1–2; S3.1 Description "adjusted kind computed alongside Tier 1"; S3.1 AC-4; F1 Output contract; F5 `adjustedKind`.
**Hole:** F1's `Recommendation` = `{kind, confidence, reason, signals}`. F3 adds no field and no second entry point, so the implementer must invent how `/evaluate` obtains both kinds for the F5 row. Worse, F3's liquidity rule changes `confidence`, its clauses change `reason`, and `bandPct`/`wideningFactor`/`shockAnnotation` change `signals` — none of which S3.1 AC-4 or S3.2 AC-6 gate behind `TIER2_ENABLED`. If any of them are served while dark, the user-visible output differs from S1.2 (confidence chip says low, reason says "thin price data") and the calibration epoch is contaminated.
**Evidence:** S1.2 AC-7 fixes `bandPct`/`wideningFactor` at 5 / 1.0 "at this tier"; S3.2 AC-2 asserts 1.5 / 7.5 for the same fixture D with no flag condition. F5: "`kind` is ALWAYS the kind the user was served" — but `confidence` and `reason` columns have no such rule.
**Proposed fix:** Add to F3 §Functionality: "Engine API: `computeRecommendation(input, market, params)` returns `{ served: Recommendation, shadow: Recommendation | null }`. With `TIER2_ENABLED` off, `served` is the full Tier 1 result (kind, confidence, reason, signals incl. bandPct 5 / wideningFactor 1.0) and `shadow` is the full Tier 2 result; on, the reverse. F5 logs `served.kind` as `kind`, `shadow.kind` as `adjustedKind`. `shockAnnotation` is computed on both and rendered regardless of the flag (it is not a verdict change)." Extend AC-4: "served `confidence`, `reason` and `signals` are byte-identical to S1.2 across the matrix."

### C1-D.8 — Locked copy cannot express sign-crossed verdicts the shift creates
**Location:** F1 locked copy table rows buy/fair/wait; F3 W1 step 4; S3.1 AC-1 "adjusted reason contains 'falling 12%'".
**Hole:** Shifting both thresholds by `shift` lets Wait occur at negative deltas (C: wait > −1 → a −0.5% ask is Wait) and Buy at positive deltas (+60%/30d: buy < +21.67 → a +20% ask is Buy). The templates hard-code "above market" / "below market" around `{X}`, so the engine would emit "−0.5% above market" or "20% below market". Example C's own Fair reason becomes "Within 9% of the 30-day market average; 30-day trend is falling 12%" — "within 9%" of a 5% band reads as a bug, and delta is measured against the live TCG mid, not a 30-day average.
**Evidence:** Recompute: C delta −0.5 → wait; monster +20 → buy. Spec §6 example for C used the form "3% below market, but the market is falling 12% / 30d" — the "but" construction was lost in the r1 lock.
**Proposed fix:** Add three rows to the locked table (owner F1/S1.3, trigger F3): wait-below: "{X}% below market, but the 30-day trend is falling {Y}%."; buy-above: "{X}% above market, but the 30-day trend is rising {Y}%."; fair: "{X}% {below/above} market; 30-day trend is {rising/falling} {Y}%." (drop "of the 30-day market average" everywhere — it is not what delta measures). Selection rule: sign of delta picks below/above; kind picks the frame.

### C1-D.9 — Uncapped shift and 3.0× stacked widening
**Location:** F3 W1 edge "monster trend"; F3 W1 step 2; F3 table (no combined cap); spec §3 Tier 2.
**Hole:** +60%/30d → shift +30 → Buy for any ask below +21.67% over market, Wait only above +35%, with the ⚠️ shock annotation on the same badge — the research the spec cites (and the public-methodology tooltip) says spikes "retrace"; the engine recommends buying into them. Separately volWiden 2.0 × confWiden 1.5 = 3.0× → half-band 15 → Buy < −25%, Wait > +15% (with −12% trend: −31 / +9); low-confidence CV is computed from < 14 points, so the volatility factor that stacks on thin data is largely noise.
**Evidence:** Recompute rows "monster +60", "max stack", "max stack falling −12". Spec never caps `trendShift`; F3 says "un-capped" explicitly, so this is a design choice, hence RULING.
**Proposed fix (RULING):** A) `trendShift = clamp(monthlyTrend × factor, −fairBand, +fairBand)` — the trend can at most move the band by its own width, so Buy never crosses +0 and Wait never crosses −0 (also dissolves most of C1-D.8). B) Zero the shift when `shockAnnotation.detected`. C) Keep uncapped (status quo). For stacking: cap `volWiden × confWiden ≤ 2.0`, or set volWiden = 1 when CV is computed from < 14 rows. Recommendation: A + "volWiden only at ≥ 14 rows".

### C1-D.10 — Real schema needs per-UTC-day dedupe and per-finish null filtering
**Location:** F3 density bullet; F1 "history (daily PriceSnapshot[] … may be sparse)"; repo `prisma/schema.prisma:23-37`, `src/app/api/prices/snapshot/route.ts:104-114`.
**Hole:** `price_snapshots` has `@@index([cardId, timestamp])` but no uniqueness on (card, day); `createMany` runs on every cron hit and every manual POST, so a day can hold N rows. Each row carries `usd` and `usd_foil` (no etched column). A foil evaluation must count only rows with non-null `usd_foil`; an etched one has no data at all. Neither F1 nor F3 says "one row per UTC day, latest wins" or "a row with null price for the requested finish is not a snapshot", so `snapshotCount30d`, confidence and density are all implementation-defined.
**Evidence:** Schema lines 23–37; route lines 104–114; `vercel.json` cron `0 6 * * *`; README advertises a manual Refresh (now gone from `src/`, but the POST route remains callable).
**Proposed fix:** In F1 (signal owner), referenced by F3: "Adapter builds `history` per `(scryfall_id, finish)`: select rows in the trailing 30 UTC days with non-null price for that finish, bucket by UTC date, keep the latest row per date. Counts, density and staleness operate on the bucketed series." Add a fixture: 3 rows on one day → count 1.

### C1-D.11 — The data the liquidity proxy assumes does not exist for most cards
**Location:** F3 liquidity bullet; F2 "fetches current price + history (existing scryfall.ts + price-history tables)"; repo `src/app/api/prices/snapshot/route.ts:42-51`.
**Hole:** The cron snapshots only cards already in `tracked_cards`; the only writer of that table is the snapshot route itself; no file under `src/` calls it with `cardIds` any more (the V1 watchlist UI that did was replaced by the V2 landing/evaluate pages); the MTGJson backfill in the action plan was never built. A first-time evaluated card therefore has 0 rows → density 0%, "thin price data", 1.5× widening, low confidence — for every card, for weeks. F3's calibration goal ("~30/50/20") and S3.2's honest copy both assume thin data is the exception.
**Evidence:** grep of `src/` for `api/prices` returns only the two route files; `TrackedCard` has no other writer; git log shows no ingest work since 2026-06-19. Could not query prod row counts (no credentials; read-only brief) — hence medium confidence on *how* empty, high on the mechanism.
**Proposed fix (RULING):** Either F2/S2.1 gains an AC "first evaluation of an untracked printing enqueues it for the daily cron (upsert `tracked_cards` + immediate snapshot)" and F3's calibration read-out is deferred until ≥ 30 days after that lands, or the Phase 1 DoD re-admits the MTGJson 30-day backfill. Also: F3's staleness rule needs a "cron dead" distinction — if `latest` is > 7d old for *every* card, show a global data-freshness banner rather than per-card "thin price data".

### C1-D.12 — Shock "7-day move" and tooltip copy are undefined
**Location:** F3 shock bullet; F3 table `shockWindowDays / shockMagnitudePct`; S3.2 AC-4; spec §10 shock row; F1 forbidden phrases.
**Hole:** Candidate definitions — `slope7dPct × 7`, `(latest − 7-days-ago)/7-days-ago`, `(max − min)/min` within 7 days, with or without the live `currentPrice` as the last point — give different magnitudes on the same data, and the behaviour when no row exists exactly 7 days back is unstated. The badge tooltip has no locked string; the spec's resolved copy ("markets typically retrace some of this within 1–2 weeks") is a forecast and would be lint-rejected under F1.
**Evidence:** Public-methodology note uses yet another rule ("single-day > 25% or 7-day cumulative > 30%"); three sources, three definitions.
**Proposed fix:** "`sevenDayMovePct = (latest.priceCents − ref.priceCents) / ref.priceCents × 100`, where `latest` is the newest real row and `ref` the newest real row dated ≥ 7 UTC days before it; null (no annotation) if either is missing. Trigger |move| ≥ 35." Locked tooltip: "Price moved {+/−X}% over the last 7 days." Add to F1's copy table.

### C1-D.13 — Volatility: minimum rows, std definition, clause trigger all missing
**Location:** S3.2 AC-2; F1 example D; F1 signals `volatility30d`; S1.2 AC-7; F1 copy "volatility clause (F3) 'price has been volatile (±{X}%)'".
**Hole:** F1 nulls history signals "where data is insufficient" but gives no minimum for CV (spec D: "CV n/a (insufficient)"). S3.2 AC-2 requires `wideningFactor` exactly 1.5 for D, which holds only if CV is null (or 1.0 under a gated formula with a flat D — F1's D is not stated as flat). Sample (n−1) vs population std changes a 30-point CV by ~1.7%, enough to move a 0.30 fixture across the cap. Nothing says when the volatility clause is emitted or what ±{X} is (CV × 100?).
**Proposed fix:** "`volatility30d` = sample std / mean of the bucketed series, null below `minSnapshotsForRange` (14) → volWiden 1.0. Volatility clause emitted iff volWiden > 1.0; X = round(CV × 100)." Mark D as "6 snapshots (any values)" once CV is null below 14.

### C1-D.14 — Thin-data copy fork and a dangling `TIER2_ENABLED` reference

## Leads checked and refuted
- "Widening before or after the asymmetry divide" — algebraically identical (`band × w / 0.6 = band / 0.6 × w`); S3.2 AC-1's −16.67 confirms the Buy side scales by `w / 0.6`. Only the formula text needs fixing (C1-D.1); no separate ordering finding.
- "Example C kind under the literal formulas" — Fair under all three readings (literal F3 volWiden: −18.22/+1.33; no widening: −14.33/−1; spec no-asymmetry: −11/−1). AC-1's *kind* is robust; only its pinned thresholds/bandPct are not (C1-D.2, C1-D.5).
- "S3.2 AC-1 CV 0.05 lands Buy" — true under both the literal (threshold −11.11, margin 0.89) and gated (−8.33) formulas; not a finding, though the literal margin is thin.
- "lowConfidenceWidening stacks multiplicatively with volWiden" — matches spec §3 Tier 2 (`fairBandPct * volWiden * confWiden`); F3 is faithful to the spec; whether to cap is a ruling (C1-D.9), not a contradiction.
- "Density counts real rows only" — F1 W1 edge cases state it explicitly ("density (F3) counts real snapshots only"); consistent across F1 and F3. The hole is per-day/per-finish bucketing (C1-D.10), not real-vs-interpolated.
- "If F5 hasn't merged, who logs the adjusted kind" — story order is S5.1 (5) → S5.2 (6) → S3.1 (7); the console-only fallback is moot. The real gap is the missing shadow-output contract (C1-D.7).
- "TIER2_ENABLED default" — S3.1 says "default off at merge", consistent with spec §10 "Tier 2 dark-launched"; the only holes are the dangling Standards reference and the flag's home (C1-D.14).
- "Is `latest > 7d` UTC days from now or from the newest snapshot" — it must be from an external clock (the newest snapshot cannot be stale relative to itself); the clock is simply unstated (folded into C1-D.6).
- "S3.1 AC-6 boundary at a shifted threshold" — the AC exists and is correct in intent; only the fixture constructibility is a trap (C1-D.15). S3.2's missing post-widening boundary AC is the gap.
