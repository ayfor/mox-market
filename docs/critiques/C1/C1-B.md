## Detail

### C1-B.1 — Finish fallback is assigned to a component that cannot perform it
**Location:** F1 §Functionality (input bullet: single `currentPriceCents`, single `history`), W1 step 2 "(after finish fallback)", W1 edge cases "foil requested but no foil price → fall back to normal + `fallbackNotice = true`"; S1.2 AC-5.
**Hole:** The caller converts one Scryfall field (`usd` / `usd_foil` / `usd_etched`) into `currentPriceCents` and passes one `history` keyed by `(scryfall_id, finish)`. If foil is requested and `usd_foil` is null, the engine receives `currentPriceCents = null` and an (empty) foil history. It has no access to `usd` or to the normal-finish history, so it can only emit `insufficient_data`; it cannot "compute on normal". Either the engine's input must carry all finishes, or the fallback must happen in the caller.
**Evidence:** F1 input contract as quoted; Standards "Snapshots keyed by `(scryfall_id, finish)`"; F2 W2 "history swaps to the new `(scryfall_id, finish)` key". The spec §7 row ("Fall back to `normal`, surface a UI warning") never said who does it.
**Proposed fix:** Move the fallback to the caller (F2's resolver): it picks `appliedFinish` (requested finish if priced, else `normal`), fetches the history for `appliedFinish`, and passes `MarketSnapshot { currentPriceCents, history, appliedFinish, requestedFinish }`. Engine sets `signals.fallbackNotice = appliedFinish !== requestedFinish` and otherwise never reasons about finishes. Rewrite S1.2 AC-5 as "given `requestedFinish: 'foil'`, `appliedFinish: 'normal'`, the recommendation computes on the supplied price and sets `fallbackNotice = true`". State explicitly that `etched`-missing also falls to `normal` (the notice template already assumes it).

### C1-B.2 — "Trailing 30 UTC days" has no anchor, and "snapshot" is not defined as one-per-day
**Location:** F1 §Functionality "all snapshot counts, confidence tiers, and density calculations use the trailing 30 UTC days"; Fields "history … 0–365 entries"; Decisions "pure functions".
**Hole:** A pure function with no clock cannot determine the window. `fetchedAt` exists but the spec (§1) says it is "used for staleness flag in UI, not algorithm" and the design does not promote it. Fixtures ("30 daily snapshots") are only deterministic if the window is anchored to an input. Second gap: the count is "snapshots" but the live table (`price_snapshots.timestamp DateTime @default(now())`) can hold several rows per UTC day (cron GET plus the manual POST route), and the MTGJson daily sync "ON CONFLICT DO UPDATE" would also re-write today's row; the engine never says whether it de-duplicates by UTC date before counting, so confidence can be inflated by duplicates. Third gap: who drops entries older than the window and what happens above 365 entries (throw, truncate, ignore) is unstated.
**Evidence:** `prisma/schema.prisma` lines 23–37 (timestamp, not date); `src/app/api/prices/snapshot/route.ts` (GET for cron and POST for manual refresh both `createMany`); `vercel.json` cron `0 6 * * *`; investigation §9 daily sync step 5.
**Proposed fix:** Add `asOf: Date` (UTC calendar day) to `MarketSnapshot` as the window anchor (default to `fetchedAt` at the call site, never `Date.now()` inside the engine). Specify: "Engine normalises `history` to one entry per UTC date (last entry wins), discards dates outside `[asOf − 29d, asOf]`, and counts the remainder as `snapshotCount30d`. Entries beyond 365 are an `InvalidRecommendationInputError`." Add a fixture with duplicate-day entries asserting the count.

### C1-B.3 — Empty history: param says 1, behaviour says 0, spec and F2 say insufficient_data
**Location:** F1 §Functionality param list "`minSnapshotsForVerdict` 1" and Confidence bullet "An empty history with a valid current price still yields a verdict"; S1.2 AC-4; spec §3 (`history.length < minSnapshotsForVerdict → insufficientDataVerdict`) and §8 (`'no history: insufficient_data'`); F2 W1 edge "no/insufficient history → `insufficient_data` panel".
**Hole:** The r1 revision note says "market-data-never-throws vs insufficient_data resolved", but the resolution reversed a spec test case without listing it under "Decisions baked in", left the param value contradicting the behaviour, and did not propagate to F2, which still routes "no history" to the insufficient-data panel. An implementer following S1.2 AC-4 and an implementer following F2 build opposite behaviours. The same revision also silently reversed spec §7/§8 "zero market price → throws" into `insufficient_data` (defensible, since spec §4 E already said so, but equally unrecorded).
**Evidence:** quotes above; spec §10 "Pending: None" means no Josh ruling exists for either reversal.
**Proposed fix (ruling):** A) Keep r1's behaviour (verdict on current price alone, low confidence): set `minSnapshotsForVerdict: 0` (or delete the param), add both reversals to "Decisions baked in" with the spec §8 rows they supersede, and change F2's edge case to "no history → normal panel, low-confidence chip, tiles show —". B) Follow the spec and F2: empty history → `insufficient_data`; delete the "still yields a verdict" sentence and S1.2 AC-4's second clause. Recommendation: A — a price-vs-market delta is still a fact, and under the 30-day ingest filter a zero-history card is a bulk card where "insufficient data" would feel broken; but it is Josh's call because it changes what users see for every card outside the ingest filter.

### C1-B.5 — F1 owns the signal math but writes none of it down
**Location:** F1 §Functionality "Signal ownership: F1/S1.2 computes every descriptive signal"; S1.2 AC-7; S1.1 AC-2 "all F1 params … snapshot minimums"; F1 param list (no `trendThresholdPct`, no `minSnapshotsForTrend`); F3 Fields table (both params listed there as F3's).
**Hole:** AC-7 demands exact values for median, range, rangePosition, slopes, volatility and trendDirection, but the design never defines: median on an even count (average of middles → half-cents vs integer `median30dCents`); `range30dCents.avg` rounding; `rangePosition` formula, clamping outside [0,1], and the zero-width case (fixture A is "flat" → `high − low = 0` → 0/0); slope method (F3 says least-squares %/day but not the percent base — first price, mean, or fitted intercept) and the 7-day variant's window; volatility as population vs sample standard deviation; `trendDirection` needs `trendThresholdPct` (±0.5%/day) and the null rule needs `minSnapshotsForTrend` (7), both of which S1.1's param list omits because the design filed them under "F3 params dark". They are not dark: F1 computes `trendDirection` and `slope*` at S1.2.
**Evidence:** spec §1 (`median30d: null if < 14 snapshots`, `rangePosition: 0..1`, "slope … smoothed" undefined); F3 §Functionality (least-squares, ≥7 snapshots); F1 edge list covers CV = 0 but not range width 0.
**Proposed fix:** Add a "Signal definitions" block to F1: `median30dCents` = lower-median for even counts (or round-half-up of the mean of the two middles — pick one); `range30dCents.avg` = `Math.round(mean)`; `rangePosition = clamp((asking − low) / (high − low), 0, 1)`, `null` when `high === low` or fewer than `minSnapshotsForRange`; `slope30dPct` = OLS slope of price on day-index over the interpolated trailing-30 series, divided by the fitted price at the window start, ×100; `slope7dPct` same over the last 7 dates; `volatility30d` = population std / mean of real (non-interpolated) prices; `trendDirection` = rising/falling when `|slope30dPct| ≥ trendThresholdPct`, else flat, `null` below `minSnapshotsForTrend`. Move `trendThresholdPct` and `minSnapshotsForTrend` into S1.1 AC-2's list. Give AC-7 a non-flat 30-snapshot fixture (flat only tests the degenerate cases).

### C1-B.6 — `high` confidence is a 30-of-30 attendance test
**Location:** F1 §Functionality "< 14 snapshots → low; 14–29 → medium; 30 → high" combined with "trailing 30 UTC days"; S1.2 AC-3 "≥30 → high".
**Hole:** With the window capped at 30 dates, `high` means every day present. If the window includes today, it is unreachable before the day's cron (currently 06:00 UTC; the MTGJson plan says 17:00 UTC with "1–2 missed publish days per quarter"). Each miss demotes every card to medium for the following 30 days. Under the spec's un-windowed rule (`history.length ≥ 30`) this did not arise; the r1 "trailing-30d counting window" created it. Whether a 29/30 card deserves "medium" is a product judgment, but the design presents the tiers as if `high` were the normal state.
**Evidence:** action file B5 ("Expect 1–2 missed publish days per quarter"); `vercel.json`; the public-methodology note says the confidence multiplier applies "when we have less than 30 days of price history", also assuming full attendance.
**Proposed fix (ruling):** A) `high` at ≥ 28 of the trailing 30 dates (one param `highConfidenceSnapshotCount: 28`), medium 14–27; B) anchor the window at `asOf − 1` day so today's missing row never counts against the card, and keep 30/30; C) accept as designed and say so in the confidence chip tooltip. Recommendation: A plus B's anchoring — both are one-line param/anchor changes and keep "high" meaning "essentially complete".

### C1-B.7 — The flagship demo is Fair under the locked bands
**Location:** F1 fixtures table row A ("7400 · 8150 · −9.20% · buy"); spec §4 Example A ("Esper Sentinel @ $74.99 … Market $81.50 … −7.99%"); repo `src/app/sample/decision-analysis.tsx` lines 780–792 (`yourPrice 74.99`, `market 81.5`, word "Buy Now"); action file C2 ("canonical URL `/Esper%20Sentinel?price=74.99`").
**Hole:** −7.99% > −8.33% → Fair. The design kept the Esper Sentinel numbers but shaved the asking price to $74.00 to preserve a Buy fixture, without saying that the handoff demo, the `/sample` page, and the canonical demo URL now show Fair. Josh will notice the first time he loads the demo with live math.
**Evidence:** recomputed: (7499 − 8150)/8150 = −7.99%; (7400 − 8150)/8150 = −9.20%.
**Proposed fix (ruling):** A) Accept: update `/sample`'s static data and the canonical URL to `$74.00` (or any ask ≤ $74.70) in F2's story; B) treat the demo as a Fair showcase (arguably more honest marketing); C) revisit `buyThresholdAsymmetry` (0.65 → −7.69% would keep $74.99 a Buy). Recommendation: A; do not tune the math to fit a demo.

### C1-B.8 — `setCode` is redundant, its default is unowned, and the repo helper sorts the wrong way
**Location:** F1 Fields "setCode … Default: cheapest non-promo"; §Functionality "optional `setCode` (defaults to the cheapest-by-USD non-promo printing)"; F2 W1 step 2 "defaults: cheapest non-promo"; repo `src/lib/scryfall.ts` `getPrintings` doc comment "sorted by USD price ascending (cheapest first)".
**Hole:** (1) `cardId` is a Scryfall printing ID, so a `setCode` that disagrees with it is a contradiction the engine cannot resolve; the design never says which wins. (2) Resolving the default requires a Scryfall prints search, which a pure engine cannot do; F2 performs it in the UI, so the F1 field table's default is at best documentation of someone else's behaviour. (3) "Non-promo" is undefined against Scryfall's fields (`promo`, `set_type ∈ {promo, memorabilia, token, …}`, `digital`), and printings with `prices.usd = null` must be excluded from "cheapest". (4) Live check: `order=usd` returns most-expensive first with null-priced printings interleaved (Lightning Bolt: `slp` promo $647.29, `lea` $626.67, `jgp` promo null, …; 24 of 70 printings null-priced, 14 promo), so `getPrintings(name)[0]` picks the most expensive promo, not the cheapest non-promo.
**Evidence:** live GET on 2026-10-04 as above; `scryfall.ts` lines 143–156.
**Proposed fix:** Remove `setCode` from `RecommendationInput` (the printing is `cardId`; keep a `setCode` on the F2 view-model if the UI wants it). Move the default to F2 with a precise predicate: among `unique=prints` results, filter `!promo && !digital && set_type ∉ {promo, memorabilia, token, minigame} && prices.usd != null`, pick min `usd`; add `&dir=asc` to the Scryfall query and fix the `getPrintings` comment. Note this is a repo defect F2's story must carry.

### C1-B.9 — Fair copy names a quantity the engine does not compute
**Location:** F1 copy table fair template "Within {X}% of the 30-day market average{; trend clause}."; §Functionality "`deltaPct = (askingCents − marketCents)/marketCents × 100`" with `marketCents` = today's TCG mid; Decisions "no predictions in copy".
**Hole:** `X` is the distance from today's mid, not from any 30-day average (`range30dCents.avg` is a different number that F1 also computes). Under the design's own "observed facts only" standard this is a false statement baked into a locked constant; Buy/Wait templates already say "below/above market" correctly. Inherited from spec §6, but the design is the layer that "ships as constants".
**Evidence:** quotes above; `/sample` renders "$81.50 AVG" for the range tile, so users will see a 30-day average figure that differs from the one the Fair sentence implies.
**Proposed fix:** fair template → "Within {X}% of market{; trend clause}."; canonical example → "Within 2% of market." Record under Decisions as a deliberate deviation from spec §6.

### C1-B.10 — Percent rounding and the zero case are unspecified
**Location:** F1 fixtures "B … −1.84% … 'Within 2%'", "A … −9.20% … '9% below market'", "D … +19.05% … '19% above market'".
**Hole:** The examples are consistent only with round-to-nearest-integer (floor gives "Within 1%", "9%", "19%"; ceil gives "2%", "10%", "20%"), but the rule is never written, and an implementer using `toFixed(0)` versus `Math.round` will differ on .5 cases. A Fair verdict with |delta| < 0.5% renders "Within 0% of market", which reads as broken.
**Evidence:** recomputed deltas above.
**Proposed fix:** "`X = Math.round(Math.abs(deltaPct))`; if `X === 0` the Fair sentence is 'At market price.'" Add it to the copy table and to the fixture matrix (e.g. 8130 vs 8150 → −0.25% → "At market price.").

### C1-B.13 — Fixture C's pinned Tier-2 thresholds contradict F3's formula
**Location:** F1 fixtures row C "slope −0.4%/day (−12%/30d), CV 0.07 … Tier 2: shift −6 → buy < −14.33, wait > −1"; F3 §Functionality "`volWiden = min(1 + CV/0.15, 2.0)`".
**Hole:** At CV 0.07, `volWiden = 1.467`, band = 7.33%. The pinned thresholds use band 5% (volWiden 1.0), copying spec §4's "CV 0.07 (low volatility) → volWiden = 1.0", which contradicts spec §3's formula. Under F3's math: wait > 7.33 − 6 = +1.33; buy < −7.33/0.6 − 6 = −18.2 (if asymmetry applies to the widened band — F3's formula drops the asymmetry entirely, a C1-C item). Kind remains Fair, but S3.x fixtures built from this row will fail.
**Evidence:** Node: `Math.min(1 + 0.07/0.15, 2)` = 1.4667.
**Proposed fix:** Either set C's CV to 0 (then volWiden = 1.0 and the pinned numbers hold) or recompute the row with band 7.33%. Cross-reference to the F3 critique for the asymmetry-in-Tier-2 question.

## Leads checked and refuted
- **Float behaviour at the exact band boundaries** — swept every integer-cent pair with `12·asking = 11·market` (buy boundary, 833,333 pairs) and `20·asking = 21·market` (wait boundary, 500,000 pairs) up to $100k: zero misclassifications with the literal formula `(a − m)/m × 100` compared against `−5/0.6` and `5`. The design's "exact equality lands Fair" holds in IEEE doubles for every reachable input; an integer formulation (`buy iff 12a < 11m`, `wait iff 20a > 21m`) would be cleaner but is not a correctness fix.
- **Fixture arithmetic** — A/C −9.20%, B −1.84%, D +19.05% all recompute exactly; `−5/0.6` and `−25/3` are the same double; `Math.round(parseFloat("81.50") × 100)` = 8150 as claimed.
