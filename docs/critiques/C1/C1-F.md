## Detail

### C1-F.1 — No story produces price history; the engine will run on empty histories in production
**Location:** Feature Breakdown header "Scope = the 8 Phase 1 tasks in the Task DB"; F2 Functionality "fetches current price + history (existing `scryfall.ts` + price-history tables)"; S2.1 "fetch current price + stored history"; action file Phase 1 B1–B7 and DoD "computed from MTGJson historical prices" / "Cards return real verdicts (not `insufficient_data`) for the populated MTGJson subset".
**Hole:** The cut assumes "stored history" exists. It does not, for any card a user will type.
**Evidence:**
- `prisma/schema.prisma`: `PriceSnapshot` is V1's wide row (`usd`, `usd_foil`, `eur`, `eur_foil`, `tix`; no etched column; `card TrackedCard @relation(... onDelete: Cascade)`), keyed by `cardId` + `timestamp`, not by `(scryfall_id, finish, date)`.
- `src/app/api/prices/snapshot/route.ts` GET (the `vercel.json` cron, `0 6 * * *`) does `prisma.trackedCard.findMany()` and returns `"No tracked cards"` when empty; the only writers of `tracked_cards` were V1's `card-search.tsx`/`dashboard.tsx` (POST with `cardIds`), deleted in cb4737d ("remove V1"). `src/store/watchlist.ts` has no importer. So history exists only for whatever Josh tracked before 2026-03-31, and only in the normal/foil columns.
- The MTGJson plan (action file B2–B7, investigation §9: narrow `price_snapshots`, `AllPrices.json` bulk ingest, 17:00 UTC sync, `getPriceHistory(scryfallId, finish)`) appears in no feature and no story. The Feature Breakdown scopes itself to the Task DB's 8 tasks; the Task DB (queried) contains exactly those 8 and nothing about ingest.
- Consequence chain: F1 design changed the spec's rule ("An empty history with a valid current price still yields a verdict"), so the DoD line "not `insufficient_data`" becomes trivially true. But with `history = []`: confidence `low` everywhere; `median30d`, `range30d`, `rangePosition`, slopes, `volatility30d`, `trendDirection` all null (S2.1 AC-2 renders four "—" tiles for every card); S3.1's shift is always 0 and S3.2's volWiden always 1.0, so the only Tier 2 effect in production is the 1.5× low-confidence widening applied to every card (bands become −12.5% / +7.5%); S5.1's `adjustedKind` differs from `kind` only for deltas in (−12.5, −8.33] or (5, 7.5]; F5 calibration data is all low-confidence. The "three signals, minimum defensible analysis" thesis collapses to one signal.
- Side defect: `etched` finish can never have history under the current schema, yet S1.2 AC-5/S2.1 AC-6 treat etched as a first-class finish.
**Proposed fix (RULING — options):**
- **A. Add F0 "Price history pipeline" before S2.1** (or at the latest before S3.1), three stories per the action file B-section: F0.1 narrow `price_snapshots` schema + baseline migration (see C1-F.6; Free tier → manual `pg_dump` first), F0.2 MTGJson bulk ingest script with `--dry-run` (Option A of the action file) and prod run only on Josh's explicit sign-off, F0.3 daily sync route at `0 17 * * *` + `getPriceHistory(scryfallId, finish)` + staleness handling. This is what the action file's DoD literally requires and what F3/F5 need to mean anything.
- **B. Floor option — accrual story** (one PR): on every evaluate, upsert today's `(scryfall_id, finish, date, price_cents)` for the resolved printing and extend the cron to re-snapshot every card ever evaluated. History starts at launch and reaches `high` confidence after 30 days; no 1.1 GiB ingest. Still needs the schema change and baseline migration.
- **C. Ship Scryfall-current-only** and rewrite the action-file DoD, F3's scope ("adapt to whether a card is trending") and the Feature Breakdown goals to say so honestly.
- Recommendation: A if Phase 1 still means what the action file says; B if the window is tight. C is only acceptable if the DoD is rewritten in the same gate, because as written the cut cannot satisfy it.

### C1-F.4 — S3.1's two Tier 2 fixtures contradict each other on asymmetry, and one cites a fixture that no longer exists
**Location:** S3.1 AC-1 "Tier-2-adjusted kind = fair (trend shift −6 → thresholds −14.33 / −1)"; AC-2 "rising-market fixture (example A history) shifts buyThreshold up so a −2% delta becomes Buy-eligible per formula".
**Hole:** AC-1 and AC-2 cannot both pass under one formula.
**Evidence (recomputed):**
- Asymmetric Tier 2 (F1 example C, S3.2 AC-1): buy threshold = −5/0.6 + shift = −8.33 + shift. AC-1: −8.33 − 6 = −14.33 ✓, wait = +5 − 6 = −1 ✓, −9.20 lands Fair ✓.
- AC-2 with a rising +8.1%/30d history: shift = 8.1 × 0.5 = +4.05. Asymmetric: buy threshold = −4.28; −2% is not < −4.28 → **Fair**, AC-2 fails. Symmetric (F3 design body, "`buyThreshold = −band + shift`"): −5 + 4.05 = −0.95; −2 < −0.95 → Buy, AC-2 passes but then AC-1's −14.33 is wrong (it would be −11). For −2% to be Buy under the asymmetric rule the monthly trend must exceed +12.67%.
- "Example A history": F1's recomputed table says A = "30 daily snapshots, flat" (the rising +8.1% history was the vault spec's A, which F1 replaced). A flat history gives shift 0, so AC-2 fails under both formulas as written.
- AC-1 does not discriminate either: under the symmetric formula −9.20 is still Fair (−11 < −9.20 < −1). Nothing in S3.1 actually tests which formula was implemented.
**Proposed fix:** FIX — rewrite AC-2 as "A-rising fixture (30 daily, slope +0.27%/day = +8.1%/30d, CV 0.07), delta −5.00%: Tier 1 Fair, Tier 2 Buy (shift +4.05 → buy threshold −4.28)", name the fixture (it is not F1's A), and add to AC-1/AC-2 assertions on the effective thresholds (expose `buyThresholdPct`/`waitThresholdPct` on signals next to `bandPct`/`wideningFactor`) so the asymmetry is observable. RULING only if Josh wants asymmetry dropped in Tier 2; recommendation: keep it (F1 example C, S3.2 AC-1 and the 2026-05-01 rationale all assume it) and correct the F3 design body formula to `−band/asym + shift`.
