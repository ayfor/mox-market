## Detail

### C1-C.1 — No price history exists for the cards users will actually evaluate
**Location:** F2 §Functionality "fetches current price + history (existing scryfall.ts + price-history tables)"; F2 W1 "no/insufficient history → insufficient_data panel"; Feature Breakdown F2 "computed from live Scryfall price + history".
**Hole:** The design assumes a populated per-card history. On main, history is populated only for `TrackedCard` rows, and nothing on main creates `TrackedCard` rows any more.
**Evidence:**
- `prisma/schema.prisma:10–37` — `PriceSnapshot` has a required FK to `TrackedCard`; columns `usd`, `usdFoil`, `eur`, `eurFoil`, `tix` — **no etched column**, so "(scryfall_id, finish)" history cannot exist for `etched` at all (F2 W2, F1 finish enum).
- `src/app/api/prices/snapshot/route.ts:42–50` — the cron (`vercel.json` `0 6 * * *`) snapshots `prisma.trackedCard.findMany()` only; `:89–102` — `TrackedCard` rows are upserted only when `POST` is called with explicit `cardIds`, i.e. V1's Refresh button. V1's UI (`src/components/dashboard.tsx`, `card-search.tsx`) was deleted in cb4737d; `src/store/watchlist.ts` is imported by nothing. The tracked set is therefore frozen at whatever V1 users added before 2026-04-25.
- F1 design: "An empty history with a valid current price still yields a verdict (low confidence, history-derived signals null)" → the launch-day experience for every card is `low` + 4 dashes. F3 (S3.1/S3.2) needs ≥7/14/30 snapshots to do anything; F3 header says "Signals already render via F2 tiles" — they will render as "—".
- S2.1 AC-3 ("insufficient-data path") does not even cover this case: per F1, `insufficient_data` fires only on missing market price, so no-history cards get a confident-looking Buy/Wait with "—" tiles — the action file's own "could've been an email" risk.
- The only populated-history plan is the MTGJson pivot: action file B2–B7 + investigation §9 (narrow rows keyed `(cardId, date, provider, finish, listType)`, `CardFinish` enum incl. `ETCHED`, `Decimal` price). It appears in none of Standards / Feature Breakdown / F2 / S2.1. Standards' stack line "daily cron snapshots price history to Supabase" reads as if sufficient.
**Proposed fix (RULING):**
- **A — Pull the MTGJson ingest into Phase 1 as S2.0** (schema migration per investigation §9, bulk 30-day ingest, daily sync at 17:00 UTC, prune). ~6–8h per the action file; needs Standards decision 4 and a `supabase db dump` before the destructive migration (gate brief rule 3). Gives real confidence tiers on day one.
- **B — Write-through tracking as the floor:** S2.1 upserts a `TrackedCard` for every evaluated printing so the existing cron starts accumulating; copy says "N days of history"; medium confidence after 14 days, high after 30; F3 effectively dark until then. Zero schema change, but etched is still unrepresentable.
- **C — Ship as designed** and accept an all-`low` launch.
- Recommend **A** if the sprint has ≥3 days, else **B** — and in either case the F2 design must state the expected launch-day data state so "thin data" is the designed path, not an edge case. Add an F2 edge case for `finish=etched` until the schema can store it (hide the option or show the fallback notice).

### C1-C.4 — The server path is unspecified and the stated constraints are false
**Location:** F2 §Functionality "Server-side: page/server action resolves card → … No client-side computation; no new API surface needed beyond the existing route handlers."; F2 §Decisions "Server-rendered recommendation (ships with HTML)".
**Hole:** "page/server action" are two different architectures with different URL shapes, caching, and testability. The implementer must pick, and the design's own requirements only fit one of them.
**Evidence:**
- `src/app/evaluate/page.tsx:12–14` renders `<EvaluatePageClient/>`; `evaluate-client.tsx:1` `"use client"`; `:375–405` `handleSubmit` mocks the market and `router.push('/${encodeURIComponent(name)}?price=${price}')`. `ls src/app` → `api/ evaluate/ sample/` — there is no `/[card]` route, so every submit on the merged page 404s today; recents rows (`:241`, `:414`) link to the same dead route.
- "Existing route handlers": `GET /api/prices/history` (by cardIds) and `POST/GET /api/prices/snapshot` (cron write). Neither resolves a name, lists printings, or computes. A server component should query Prisma directly, not fetch its own JSON API. "price-history tables" — there is one table.
- Standards: "RSC-first; server components for reads, Server Actions / route handlers only where interaction demands". F1 §12: "server-side, so the verdict ships down with the rendered HTML". S2.1 AC-1: "verified via RSC payload" — presupposes an RSC render; a server action's return value is not an RSC page payload.
- F2's W2 (switch set → recompute) + "skeleton on submit, previous result cleared" + "ships with HTML" are jointly satisfiable by searchParams-driven RSC with Suspense, not by a server action returning data to client state.
**Proposed fix (FIX — Standards' RSC-first rule implies it):** Replace the sentence with: "URL contract `/evaluate?card=<exact name or scryfall id>&set=<code>&finish=normal|foil|etched&price=<decimal>`. `page.tsx` is an async RSC: parse + validate `searchParams` → `<Suspense key={paramsKey} fallback={<PanelSkeleton/>}>` → async `<RecommendationPanel/>` → `loadMarketSnapshot()` (Scryfall + Prisma directly) → `computeRecommendation()`. The client form and the set/finish selectors only `router.push` new params inside `useTransition` (pending → skeleton; the `key` unmounts the previous panel, satisfying AC-8). Printings arrive as RSC props. The one new route handler is `GET /api/cards/autocomplete` (see C1-C.10)." This also makes evaluations linkable (F7 later) and AC-1 literally testable.

### C1-C.5 — "Cheapest non-promo printing" cannot be computed from what the repo has
**Location:** F2 §Fields set "cheapest non-promo"; F2 W1 step 2 "defaults: cheapest non-promo, normal"; S2.1 AC-10 "cheapest-by-USD non-promo printing … fixture card with promo + non-promo printings".
**Hole:** The lead ("no prints function") is refuted — `getPrintings()` exists — but its semantics are the opposite of what the design needs, the type lacks every field the rule depends on, and the rule itself is under-specified for real print lists.
**Evidence (live api.scryfall.com, 2026-10-04):**
- `!"Esper Sentinel"&unique=prints&order=usd` (exactly what `src/lib/scryfall.ts:144–155` sends; JSDoc says "sorted by USD price ascending (cheapest first)") returns: `sld 2123` (usd **null**, usd_foil 98.00, finishes `[foil]`) → `pmh2 12s` (promo **true**) → `plst MH2-12` 66.66 → `mh2 328` 61.23 → `h2r 2` 59.52 → `mh2 12` 59.17 → `j21 75` (digital, no prices). Descending on a blended price; `[0]` is a foil-only Secret Lair. With `dir=asc` the digital no-price card sorts first.
- `src/types/scryfall.ts:65–113` has no `promo`, `promo_types`, `finishes`, `prints_search_uri`, `games`, `prices.eur_etched`; only legacy `foil`/`nonfoil` booleans. Scryfall docs: `promo` "True if this card is a promotional print"; `finishes` "flags that indicate if this card can come in foil, nonfoil, or etched"; `prints_search_uri` "where you can begin paginating all re/prints".
- `/cards/named?exact=` returns one default printing (`mh2 12`), not the cheapest — so "card search → picks card" does not yield the default set by itself.
- `set_type:"promo"` and `promo_types:["boosterfun"]` appear on non-promo cards; `promo` boolean is the right filter. Workflows note Procedure 3 says "DEFAULT to most recent standard printing" — a third definition.
- AC-10's fixture (promo + non-promo) would not catch the foil-only or digital cases that the live data actually contains.
**Proposed fix (FIX):** Specify `pickDefaultPrinting(prints, finish)`: candidates = prints where `promo === false && digital === false && games.includes('paper') && finishes.includes({normal:'nonfoil',foil:'foil',etched:'etched'}[finish]) && prices[{normal:'usd',foil:'usd_foil',etched:'usd_etched'}[finish]] !== null`; pick min price; tie → earliest `released_at`; none → use the `named?exact` card and let the engine's fallback/insufficient path speak. Fetch prints via `prints_search_uri` (oracle-id based) rather than `!"name"`. Extend `ScryfallCard` with the five fields. Fix `getPrintings` (JSDoc or `dir=asc`). Fixture = this Esper Sentinel list: expect `mh2 12` for `normal` ($59.17) and `mh2 12` for `foil` ($76.47, cheapest non-promo foil).

### C1-C.8 — Which clock drives the 36h staleness flag?
**Location:** F2 §UI "fetchedAt staleness flag when > 36h"; F2 §Decisions "staleness flag at 36h"; F1 `MarketSnapshot.fetchedAt` "Last refreshed (used for staleness flag in UI, not algorithm)".
**Hole:** One `fetchedAt` field, two data sources with different clocks, and a third case (no history) with no clock.
**Evidence:** Current price: `getCardByName` at request time → `fetchedAt = now`, never >36h; Scryfall's card object carries no price timestamp (docs: "daily price information"). History: `PriceSnapshot.timestamp` written by the 06:00 UTC cron → healthy max age ≈ 24h, so 36h ⇔ exactly one missed run (sane threshold — not a finding). Untracked card → no rows → no timestamp. F3 adds "latest > 7d old → confidence caps at low" on the same field (a second rule); `evaluate-client.tsx:29` `STALE_MS = 24h` on recents (a third). If MTGJson lands, `fetchedAt = meta.date` (publish ~14:00 UTC, sync 17:00) and 36h ⇔ one missed publish — still sane.
**Proposed fix (FIX):** F2 defines: `fetchedAt = max(history.timestamp)` for `(cardId, finish)`, else `null`. Footer: "Market price via Scryfall (TCGplayer), updated daily · Price history: N snapshots, newest {relative time}". Flag iff `fetchedAt !== null && now − fetchedAt > 36h`; when `null` render "no price history yet for this printing" (not a stale flag). Keep F3's 7-day confidence cap separate; put both constants in `RECOMMENDATION_PARAMS` (or a UI consts module). Delete or align the recents 24h constant.

**Location:** F2 §Functionality "Input handling: card search (existing autocomplete), set + finish selectors, asking-price field"; Standards "existing wrapper with throttle + card cache".
**Hole:** The story is sized as "wire the engine in"; it is actually "build the evaluation inputs".
**Evidence:** cb4737d deleted `src/components/card-search.tsx` (563 lines) and `suggestion-list.tsx`; `autocomplete()` in `scryfall.ts:57–68` is a lib function imported by nobody that swallows errors (`return []`), so "Scryfall down" during typing is silent. `card-cache.ts` is `localStorage`-only (`typeof window` guards) — client-side V1 residue, useless to an RSC. `/evaluate:147–156` is a plain `<input type="text">`; `/sample:31–37` set picker is five constants; finish is a boolean foil checkbox (no etched).
